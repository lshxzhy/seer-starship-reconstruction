# 接手续建 SEER

先运行 `python work/assemble-seer.py`，打开 `outputs/seer-starship.html`。点三维画面后按 WASD 移动，或点按屏幕方向键。按 M 打开舰内地图找舱室，按 B 查看背包，舰体观察工具归入终端。

## 项目文件从哪里改

- 游戏和飞船的源代码放在 `src/`；构建脚本列出离线包各个模块的装配顺序。游戏结构变更从所属源文件开始，构建命令见[项目首页](../README.md)。
- `work/` 保留构建入口、随包的 Three.js 及开发工具。构建会合成 `outputs/seer-model.js`、供本机服务使用的 `work/seer-fragment.html` 和可双击的 `outputs/seer-starship.html`。下一次构建会重写这三个文件。
- 发布页提供独立 HTML 和由该版 Git 提交导出的本地运行包。历次原项目截图、驾驶录像留在对应版本的发布附件。原游戏的第三方图片与录像请按[资料索引](SOURCES.md)回到出处。

## 各模块由谁负责

|制作职责|文件|交付范围|
|---|---|---|
|公共舱| `src/habitat/civic.js` |传送舱、教官办公室、荣誉大厅、瞭望露台|
|科研与指挥| `src/habitat/science.js` |船长室、实验室、资料室、瞭望舱|
|动力与检修| `src/habitat/engineering.js` |动力室、机械室、发明室|
|全舰总装| `src/habitat/installation.js`、`kit.js`、`layout-record.js` |甲板、公共门洞、通道、碰撞、坐标及交通；跨舱连通由此处统一处理|
|赛尔与驻舱| `src/population/robot.js`、`population.js`、`player.js`、`berths.js` |机体、屏面和步态、船员近场实例、玩家镜头与充能位|
|随行伙伴| `src/population/super-nono.js` |第一代初级超能 NoNo 的白壳、黑屏、青翼、伴行与致意|
|机械室采样| `src/habitat/engineering.js`、`src/population/mining-drill.js`、`src/viewer/boarding.js` |机务舱布置领取工位和三块训练样品，角色模块装配双臂钻头，玩家靠近工位后领取或采集|
|滑翔翼与驾驶| `src/population/personal-flyer.js`、`src/viewer/personal-flight.js` |前者负责实体、踏板高度和悬浮表现，后者负责取出、登乘、净空、升降、着陆和存档|
|操控与视图| `src/viewer/boarding.js`、`explore.js`、`work/seer-layout.html` |登舰、视角、定位和全舰浏览|
|舰载界面| `src/viewer/flight-deck.js`、`ship-map.js`、`inventory.js` |终端负责面板和入口，地图读取安装总图，背包读取玩家物品与装配状态|
|舰体和装配| `src/ship/`、`src/habitat/exterior-scale.js`、`work/assemble-seer.py` |舰壳、外构件、涂装、舰内总体布局、米制标尺和离线构建|

地图界面从 `habitat.plan` 读取房间、充能分区、门位和升降线，点击舱室后把稳定 ID 交回登舰控制器。改舱门或停靠层时，先更新总装数据。背包通过玩家状态取得座驾、钻头和训练矿样，并把穿戴、使用动作交回控制器。场景工位的可领取条件和矿样计数在 `boarding.js`，持久化接口在 `pilot-locker.js`。单文件版由 `offline-locker-host.js` 经外层页面保存这份小型装备记录。本机服务使用浏览器储存；聊天预览的状态随宿主保存能力恢复。浏览器限制储存时，仍可在当前页面内使用装备。

## 轿厢和层站

两条线的安装坐标仍来自总装的站表。`src/habitat/lift-plant.js` 建造井架、齿条、轿体、厅门和轿门，并把开门净宽、车底位置用于步行碰撞。`src/viewer/lift-ride.js` 为每条线维护一台车的停站、门行程、速度和沿轨位置。登舰控制器在乘车时用同一位置移动玩家、镜头和超能 NoNo，平层开门后恢复甲板行走。维护这段流程时，共用真实停站数据和轿厢净尺寸；米制站位、乘梯操作与时间见[舰内升降系统](舰内升降系统.md)。

## 运输路标与交付

`wayfinding.js` 和地图共用安装表与换乘计算。舱门、主廊岔口、升降站的牌面和地箭在本层米制空间绘制，走偏时会从实际位置重新接路。终点站位由动力室三维柜台与步行交互共用。改动柜体时同步检查柜前净空、可触发距离和标牌视线。

`exchange.js` 负责现场选择和确认，`boarding.js` 按真实位置、现有库存与已签收量落账。矿架按累计开采量隐藏矿块；背包显示尚未交付的数量。奖励和回执从每笔签收数量计算。存档迁移、数量上限与重复写入合并在 `locker-record.js`，浏览器版可读取 v0.5 的装备记录。兑换依据和缺少的角度见[原作图证](动力室物资兑换图证.md)。

## 改动怎样接入成品

舱室由稳定 ID 注册，例如 `cabinBuilders.teleport = function (kit) { ... }`。装配顺序由构建脚本定义。局部原点在舱室地面中心，单位为米，Y 向上，+Z 指门口。公共门净宽 3.4 米、高 3.1 米。每个舱传入自己的 W、D、H。公共壳体负责地面和门洞；舱内大型设备在 `kit.block(x,z,w,d)` 登记占地，使玩家能从入口走到工位并绕回。新开出口须同步设计两端落点、朝向和碰撞。

十一处游戏舱室和四层驻舱共用 `installation.js` 的米制坐标。同层通路从舱门经支廊接入主廊，机械室与传送舱的门在主廊两侧相对。跨层由塔桥主升降机和底层至腹舱的检修升降机接驳。停靠层选择只在玩家进入已开门的轿厢后出现。七处工程规划区仍只在分层总图显示。瞭望舱阶梯顶标着“机械室”的锁闭门保留了原作画面，要去机械室须走公共通路换层。

玩家和船员共用 `seerRobots` 模板。第一人称眼位读 `eyeHeight`，步态读 `phaseStep`。需要改体型时同时看正面剪影、侧面轮廓、鞋底触地和光学面盘高度。人口层只绘制近场实例，远程船员的位置由同一时钟与路线求得。

v0.4.0 的玩家面盘由 `seerRobots.setExpression(rig, 'smile')` 切到笑眼，传入 `'neutral'` 恢复平视。玩家的步态更新同时推进眨眼，批量船员共用常态屏。2014 年对白画面的笑眼可以作为绘制依据，地图上原版表情菜单的触发方式还有待录到。[面盘表情图证](面盘表情图证.md)

伙伴由 `createSuperNono(worldMetre)` 单独创建。登舰和换层使用 `arrive` 安排队形，逐帧 `update` 读取玩家位置、视角、骑乘状态和踏板高度，`greet` 触发致意。更改绕障或飞行队形时，保留同一只 NoNo 在徒步与驾驶之间的连续性。[超能 NoNo 图证](超能NoNo图证.md)

滑翔翼以甲板坐标定位，局部 −Z 为机鼻，中央为双脚落点。实体的 `update` 返回相对当前甲板标高的踏面高度，包含地面构件、飞行高度和悬浮起伏。驾驶时赛尔压低机体，双脚落在踏板上。玩家、镜头和伙伴共用这项高度基准。机身宽约 2.98 米、长约 2.26 米，最远翼端距中心约 1.548 米。碰撞圆半径取 1.60 米，允许低空居中穿过净宽 3.40 米的标准舱门。制作新舱时应在 `kit.block` 登记机柜占地，给取出、下机留下开阔甲板。[单人飞行器图证](单人飞行器图证.md)

本期键位由 `boarding.js` 统一接入。步行和快行分别为 3.6 和 6.8 米/秒，滑翔翼正常与加速上限分别为 8.2 和 11.5 米/秒。F 根据状态取出、登乘或着陆，驾驶时空格上升、C 下降。触屏按钮复用同一套取出和升降操作。画质固定为精细。后续造型或操作补证接在 [#6](https://github.com/lshxzhy/seer-starship-reconstruction/issues/6)。

角色资料从 [characters.json](../src/ai/characters.json) 读取。稳定角色 ID 对应联系人，`departmentId` 对应功能分组，`roomId` 对应模型舱室；外部联系人可没有舱室。原作依据写进 `facts` 和 `sources`，项目拟定的语气及专长写进 `persona` 和 `expertise`。补资料时同步[角色说明](舰上组织与角色.md)。普通船员复用 `crew`，会话按实际 SE 编号区分。

本地对话由 `src/ai/server.py` 提供同源登舰页和流式接口，`dialogue.js` 处理选角、输入、停止和页面内会话。每次舰上请求显式发送 `think: false` 和 `options.num_ctx: 8192`，思考设置仅作用于本项目的角色通讯。角色直接以中文生成同人对白。接手时从项目根运行 `python src/ai/server.py --open`，从舰内按钮实际发送消息；浏览单文件离线版时，运行入口见其通讯提示。只将公开角色资料和运行方法写入仓库。

## 贡献一次改动

近景材质的颜色、粗糙度和浮雕由 `kit.js` 按米制铺设；玩家清漆、底箍、密封圈和面盘分层在 `robot.js`。天空在 `src/viewer/orbit-sky.js`，舰内与舰外分别使用 `lighting.js` 的反射环境。`finish.js` 用主场景的同一张深度图计算精细档的接触遮蔽，再处理边缘。舱室大件的方向阴影在换舱时更新。精修一个工位时，在第一人称门口确认整体轮廓，再近看构件的真实嵌装、受光和遮挡；对颜色有判断时附同机位游戏出处与当前模型画面。

1. 在对应 Issue 留下舱名或角色、准备解决的问题、负责文件和依据，确认该文件当前的制作人。基于主线建分支，例如 `room/machine-arrival`。
2. 为每个观察记录游戏版本或来源发布日期、页面链接或视频时间码、进入动作、出发房间和到达房间。把能看见的构件与必须补画的背面分别记下。自录时保留一份本地原始材料，公开文档只放有权分发的内容，避开账号、聊天和个人标识。
3. 在所属源文件制作，从离线入口核对实际使用的视角。提交 PR 时说明原图的哪一处促成了哪项修改、从哪里能看到结果，以及仍欠哪个角度。总装维护者合入后在原 Issue 留下提交、交付物与下一步。

若暂时不能进入相符版本的客户端，可先交付查过的历史图文和可再次定位的录像时间码。当前 H5 和经典页游分别建记录，接手人从最近一个已确认的落点继续。
